# Multi-peer golden (Layer B) — manual toolkit

**Manual only.** No nightly, no PR gate. Full matrix via local
`just golden-all-peers` or GitHub Actions `workflow_dispatch` with
`run_all=true`.

## Layers

| Layer | What | Proves |
|-------|------|--------|
| **A** | Real DDL fixtures + Tiqora only (`SCHEMA_MATRIX=1`) | Detect, migrate, R/W on schema |
| **B** | Real peer app container + Tiqora on same DB | Behavioural parity (TN, history, escalation, …) |

Layer A covers all profile fixtures under
`backend/tests/fixtures/legacy-schema/`. Layer B runs a **real** OTRS/Znuny
container from a release tree listed in `peers.yaml`.

`test_process_deploy.py` proves Tiqora's process/ACL dumps equal Znuny's `ProcessDump`/deployed ACL file, the deploy watcher snapshots Znuny deploys, and a new process ticket writes Znuny's history and dynamic field values (znuny-6.5: passed; 7.3: passed (cached peer image `tiqora-golden-peer-znuny-7.3`, built 2026-07-27, Znuny 7.3.5), 2026-10-09).

`test_process_designer.py` covers the wave-3 process designer against the peer: a Znuny export
(`ProcessImport` of every sample in `scripts/test/sample/ProcessManagement/`, then `_GetProcessData`
and `YAML->Dump`) imported and exported again by Tiqora is equal modulo ids/times/list order; a
Tiqora edit is a draft (`not_sync`) in Znuny; a `signal` deploy ends in `ZZZProcessManagement.pm`;
everything Tiqora writes loads with Znuny's `YAML->Load` and `ProcessDump(HASH)` equals
`build_process_dump`; `AppointmentCreate` writes the same `calendar_appointment` columns; the
`Module` condition with an unknown module does not crash; an attachment option key generated by
Znuny resolves to the same bytes in Tiqora. `test_tiqorasync_deploy.py` adds the end-to-end case
`deploy_from_tiqora(mode="signal")` -> `Run()` -> status `ok`. Both passed on `znuny-6.5` and
`znuny-7.3` (cached peer images, 2026-10-12) with no peer-specific difference.

**TiqoraSync in the peer.** The peer image does not ship the add-on. The two modules above copy
`packages/znuny-addon/TiqoraSync/Kernel/System/TiqoraSync.pm` into `/opt/otrs/Kernel/System/` with
`docker compose cp` (`_helpers.znuny_copy_in`) in a module fixture, drive it the way the daemon cron
task does (`$Kernel::OM->Get('Kernel::System::TiqoraSync')->Run()`) and delete it again at teardown.
`TIQORASYNC_MODULE=<path>` points at another copy of the module. The fixtures also create the
`tiqora_*` tables the golden DB lacks (settings, cache signals, revisions) and drop them again; rows
they add to existing tables, the dynamic fields, calendars and tickets they create are removed, and
the sample process is restored to its imported state.

**A peer without its source tree.** `just golden-up` needs the release tree for `--build`. The
source trees are gitignored and exist only in the main checkout, so a worktree starts a cached peer
image without building: `docker compose -p "$GOLDEN_COMPOSE_PROJECT" -f tests/golden/docker-compose.golden.yml up -d --no-build --wait`
(after `eval "$(python3 tests/golden/peer_env.py <peer>)"` and exporting `GOLDEN_PEER`,
`GOLDEN_SOURCE_DIR`, `GOLDEN_COMPOSE_PROJECT`), then `just golden-seed` on a fresh volume.

## Peers

See `peers.yaml` for ids (`otrs-znuny-6.0` … `znuny-7.3`). Default:
`znuny-6.5` → source dir `znuny-6.5.22/` at the repo root (gitignored).

```sh
just golden-peers          # all ids
just golden-peers-ready    # ids with source present
GOLDEN_PEER=znuny-6.5 just golden-peer-env
```

## Source trees

Place a **real directory** (not an external symlink — Docker `COPY` rejects
those) at the path given by `source_dir` in `peers.yaml`:

```text
znuny-6.5.22/          # primary peer
znuny-6.0.45/          # optional further peers
…
```

Each tree needs `scripts/database/schema.mysql.sql` or
`scripts/database/otrs-schema.mysql.sql` (pre-6.4 naming).

## Local recipes

```sh
# Default peer (znuny-6.5)
just golden-up
just golden-seed
GOLDEN=1 just golden-test   # or: just golden-test  (exports GOLDEN=1)
just golden-down            # keep volume
just golden-clean           # drop volume

# One-shot
GOLDEN_PEER=znuny-6.5 just golden-run

# Other peer (source must exist)
GOLDEN_PEER=znuny-7.0 just golden-run

# Every peer with source on disk (sequential, tear-down between peers)
just golden-all-peers
```

Compose project name is `tiqora-golden-<peer>` with dots replaced by
hyphens (e.g. `tiqora-golden-znuny-6-5`) so volumes/images stay isolated
per peer. Host ports stay `3307` (MariaDB) and `8180` (HTTP) — only one
peer stack at a time.

Low-level:

```sh
eval "$(python3 tests/golden/peer_env.py znuny-6.5)"
docker compose -p "$GOLDEN_COMPOSE_PROJECT" \
  -f tests/golden/docker-compose.golden.yml up -d --build --wait
```

## Env

| Variable | Purpose |
|----------|---------|
| `GOLDEN=1` | Un-skip golden pytest modules |
| `GOLDEN_PEER` | Peer id from `peers.yaml` (default `znuny-6.5`) |
| `GOLDEN_DB_URL` | Shared MariaDB URL (sync) |
| `GOLDEN_DB_ASYNC_URL` | Shared MariaDB URL (async / Alembic) |
| `GOLDEN_COMPOSE_PROJECT` | Set by `peer_env.py` |
| `GOLDEN_SOURCE_DIR` | Build-arg path relative to repo root |

## CI (manual)

`.github/workflows/golden.yml` — **workflow_dispatch only**:

| Input | Meaning |
|-------|---------|
| `peer` | Single peer id (default `znuny-6.5`) |
| `run_all` | Sequential run of all peers with source present |

Runner must have the release tree(s); otherwise the job fails the source
check. Local `just golden-all-peers` is the usual full-matrix path.

## Adding / validating a peer

1. Add entry in `peers.yaml` (`source_dir`, `schema_profile`, …).
2. Extract release tree at `source_dir` (real dir, not external symlink).
3. `GOLDEN_PEER=<id> just golden-run` and fix any intentional behavioural
   deltas only with documented pins.
4. TiqoraSync Framework tags already cover 6.0–7.3
   (`packages/znuny-addon/TiqoraSync/`).

## Implementation notes

- One Dockerfile (`Dockerfile.znuny`) with `SOURCE_DIR` build-arg; install
  home inside the image is always `/opt/otrs`.
- Entrypoint auto-detects `schema.mysql.sql` vs `otrs-schema.mysql.sql` and
  Console (`znuny.Console.pl` / `otrs.Console.pl`).
- `_helpers.py` / `seed.sh` honour `GOLDEN_COMPOSE_PROJECT` so multi-peer
  stacks do not cross-talk.

## ITSM peers

`znuny-6.5-itsm` and `znuny-7.3-itsm` (`base:` + `itsm: true` in `peers.yaml`) are the plain 6.5 /
7.3 peers plus the official Znuny ITSM packages. They reuse the base peer image
(`tiqora-golden-peer-<base>`), run in their own compose project and DB volume, so the plain peers
stay ITSM-free. Same host ports as every peer: one peer per session.

```sh
just golden-itsm-fetch znuny-6.5-itsm              # download + sha256 verify + unpack (once)
GOLDEN_PEER=znuny-6.5-itsm just golden-up          # installs the packages on first start
GOLDEN_PEER=znuny-6.5-itsm just golden-seed
GOLDEN_PEER=znuny-6.5-itsm just golden-test        # whole suite; ITSM tests only:
cd backend && GOLDEN=1 GOLDEN_PEER=znuny-6.5-itsm uv run python -m pytest -q -m golden ../tests/golden -k itsm_peer_smoke
```

- `itsm-packages.yaml` lists the packages per base peer with version, URL and sha256 (first
  fetch: `just golden-itsm-fetch <peer> --record`; later fetches fail on a mismatch).
  `fetch_itsm_packages.py` writes `tests/golden/itsm-packages/<base>/` (the `.opm` files plus
  `install-order.txt` / `provides.txt`, mounted read-only at `/opt/itsm-packages`) and unpacks
  every `.opm` into `tests/golden/itsm-packages/src/<Package>-<version>/` for reading. The
  directory is gitignored; the sources are never executed by Tiqora.
- `znuny-entrypoint.sh` (bind-mounted by compose, so a cached image needs no rebuild) installs the
  packages with `Admin::Package::Install` in `install-order.txt` order when `GOLDEN_ITSM=1`, then
  `Maint::Config::Rebuild` and `Maint::Cache::Delete`. It is idempotent: a restart installs
  nothing. The package files live in the container, the repository rows in the DB volume; a
  recreated container on a kept volume therefore runs `Admin::Package::ReinstallAll` instead.
- `just golden-up` falls back to the cached image (`--no-build`) when the release tree is absent,
  as in a worktree.
- Plain and ITSM tests cannot share a session: tests carry the marker `itsm_peer` or `plain_peer`
  and are skipped on the other kind (`conftest.py`); the fixture `golden_peer_id` returns
  `GOLDEN_PEER`. Plain-peer assertions run in a `GOLDEN_PEER=znuny-6.5` session.
- `itsm_seed.pl` (copy in with `znuny_copy_in`, run with `znuny_perl_eval`) creates service
  `itsm94-svc-web` (criticality `4 high`), SLA `itsm94-sla-web` (`MinTimeBetweenIncidents` 120),
  `Computer` CIs `web01.example.org` (2 versions) and `db01.example.org` (3 versions), a `Network`
  CI `net01.example.org` in incident state, service->CI, CI->CI (`DependsOn`) and ticket->CI
  (`RelevantTo`) links, all addresses from 192.0.2.0/24. Re-running changes nothing and prints
  the ids as JSON between `GOLDEN_ITSM_SEED_BEGIN` / `_END`.
- `test_itsm_peer_smoke.py`: packages installed (`Admin::Package::List`), the six core ITSM tables
  exist, seed results (`ConfigItemSearchExtended`, `LinkList`), seed idempotence, and on a plain
  peer no ITSM tables or packages.

- `test_itsm_mode_a.py` (Task 28): Mode A parity on `znuny-6.5-itsm` and `znuny-7.3-itsm`
  (detection, CI search / detail / versions vs `ConfigItemSearchExtended` / `ConfigItemGet` /
  `VersionGet`, ticket-CI links both ways, link and ticket-history parity with `LinkAdd` /
  `LinkDelete`, the documented `configitem_history` difference, the 25 matrix cells, service
  incident state, "Mode A writes no ITSM table") plus the setup cases. The "ITSM peer + plain
  peer" case is split in two (the toolkit runs one peer per session):
  `test_setup_on_itsm_peer_is_noop` runs on an ITSM peer, `test_setup_on_plain_peer_equals_itsm_packages`
  and `test_znuny_reads_tiqora_seeded_dynamic_fields` on a plain peer (`GOLDEN_PEER=znuny-6.5` or
  `znuny-7.3`); each is skipped on the other kind. Tiqora's writes reach Znuny's cached reads only
  through the TiqoraSync add-on, so the module copies `TiqoraSync.pm` into the peer for its run and
  calls `Run()` after Tiqora writes (as the daemon cron task does). The module's own data is the
  service `itsm28-svc` (child `itsm28-kid`) and the CIs `itsm28-a|b|c.example.org`; every ticket
  and link a test creates is removed again, the plain-peer cases delete the rows setup created.
  `conftest.py` resolves the schema profile of an ITSM peer through its base peer
  (`znuny-6.5-itsm` is no profile id). Results (2026-10-13): all cases passed on `znuny-6.5-itsm`
  and `znuny-7.3-itsm` (13 cases, 11 run on an ITSM peer), the two plain cases on `znuny-6.5` and
  `znuny-7.3`; differences between Tiqora and Znuny are listed in `docs/itsm-import.md`.

- `test_tiqoraitsm_addon.py` (wave-4 import Task 26): the `TiqoraITSM` add-on (ticket zoom widget
  "Betroffene CIs (Tiqora)", `Kernel::System::TiqoraITSM`) copied into the peer, SysConfig rebuilt,
  widget driven with a real `Kernel::Output::HTML::Layout`. The module creates the CMDB rows, an
  agent without access to the secret class group and (if absent) the tables/views, and removes
  all of it again. Results (2026-10-13): 11 passed on `znuny-6.5` (plain, fresh DB: tables and
  views created by the module) and on `znuny-7.3-itsm` (7.3 framework; the add-on does not read
  `configitem`, so a plain `znuny-7.3` behaves the same; not run separately).
  Task 27 extends it (29 cases): the read-only guard (`PreApplicationModule###TiqoraITSMReadOnly`,
  incl. `AgentLinkObject` towards CIs), the customer page and the optional linking
  (`AgentTiqoraITSMLink` posts cmdb's `LinkIn` with the bearer key to the recording sink
  `gisink`; refuses GET, a missing challenge token, agents without ticket `rw`, bad ids). The
  module creates and deletes one ticket and one `customer_user_customer` row. Results
  (2026-10-13): 29 passed on `znuny-6.5` (plain) and on `znuny-7.3-itsm`.

- `test_itsm_import.py` and `test_gi_config_items.py` (wave-4 import Task 28; shared helpers in
  `_itsm_import_support.py`): the Znuny ITSM importer and the GenericInterface `ConfigItem*`
  operations against the real data of an ITSM peer. The data is created through
  `Kernel::System::ITSMConfigItem` in the peer (so the XML storage is what Znuny writes): the
  custom class `GoldImpAppliance` (nested `Sub` attribute, `CI` reference, `GeneralCatalog`,
  `Integer`, `Date`, `DateTime`) next to the default class `Computer`, five CIs with 1-3 versions,
  CI<->CI (`DependsOn`, `RelevantTo`) and ticket->CI links and one binary attachment.
  `test_itsm_import.py` runs `run_import` (page size 2) and compares Tiqora's rows with Znuny's
  `VersionList` / `VersionGet(XMLDataGet => 1)` / `link_relation` + `LinkList` / attachment bytes:
  dry run writes nothing, version counts, names, states, times, authors and attributes
  (`xmldata_to_attributes`, plus literal checks of the converted CI reference, catalog id, nested
  attribute, integer, date, datetime), links (a type with equal source and target name, like
  `RelevantTo`, has no direction in Znuny; Tiqora stores it CI first), second run only
  `unchanged`, a new Znuny `VersionAdd` adds exactly one version, nothing is written to Znuny.
  `test_gi_config_items.py` imports a REST webservice (`webservices/GoldenConfigItemREST.yml`,
  the five `ConfigItem::*` operations) into the peer, imports and switches the site to Mode B
  (`switch_to_tiqora`) and compares Znuny's answers with Tiqora's on the same webservice row and on
  the canonical `/znuny-compat/ConfigItem...` routes: `ConfigItemGet` of all five CIs (also a
  comma list with `Attachments`), `ConfigItemSearch` (class, name, states, `CIXMLData`, order,
  limit), error bodies of missing parameters, `ConfigItemUpdate` (one new version on each side, equal
  result) and the `ConfigItemUpdate` process action (scenario 2 of Znuny's
  `TransitionAction/ConfigItemUpdate.t`, `Run()` against `execute_transition_action`, smart tag
  `<OTRS_TICKET_Title>` included). Both modules snapshot the `tiqora_*` tables the importer writes
  and the `itsm.*` settings and restore them, delete their Znuny CIs, ticket and webservice. What
  stays in the peer: the general catalog item of the class `GoldImpAppliance` (Znuny cannot delete
  one) and the agent `goldimp.agent` (needs `itsm-configitem` rights; users cannot be deleted).
  The modules run on a peer that holds other CIs (the counters are checked against what the peer
  holds; content only for the module's own CIs). Results (2026-10-13): 35 cases (6 + 29) passed on
  `znuny-6.5-itsm` (image `tiqora-golden-peer-znuny-6.5`, ITSM bundle 6.5.3) and on
  `znuny-7.3-itsm` (image `tiqora-golden-peer-znuny-7.3`, ITSM 7.3.x); both runs with commit
  `cbc7c960e` of `wave4-cmdb-postfix` (CMDB-PM-I1: optional imported attributes are not mandatory)
  applied, without it `ConfigItemUpdate` and the process action fail on the imported `Computer`
  class. Differences found, fixed in the owning modules (with unit vectors there):
  `virtual_fs.backend_key` of Znuny's DB backend is `Compress=0;Crypt=0;FileID=3;Mode=binary;`
  (the importer read it as a bare number and reported every attachment as "in the file system"),
  a link seen from both CIs' pages was counted twice in the report, and `ConfigItemGet`
  `Attachment.Preferences` carry `ContentID`/`UserID` (no human-readable `Filesize`). Differences
  that remain, documented: Znuny answers an error with HTTP 200 and Tiqora with 4xx; Tiqora
  expands the `$Self->{OperationName}.AuthFail` code Znuny sends unexpanded and answers
  `<Op>.AuthFail` where Znuny's Search/Create/Update check `UserLogin`/`Password` themselves
  (`MissingParameter`); Znuny keeps an empty text value after `Vendor::1 = ''`, Tiqora removes the
  value (the comparison hides empty values in `CIXMLData`).

Measured 2026-10-12 (cached base images, so no image build; `golden-up` includes package install
and `--wait` for the healthy peer): `znuny-6.5-itsm` 43 s, `znuny-7.3-itsm` 57 s, a plain peer
12 s. Smoke test: 4 passed on each ITSM peer, 1 passed (3 skipped) on `znuny-6.5`.

Fallback if a download disappears: build the `.opm` from the `github.com/znuny/<Package>` tag
inside the base peer (`Dev::Package::Build <Package>.sopm <dir>` with the checked-out tree),
put it into `tests/golden/itsm-packages/<base>/` and record its sha256 in `itsm-packages.yaml`.
Not needed so far.

Things worth knowing for the survey (Tasks 2 and 3): with ITSMCore installed the core
`Kernel::System::Service` / `SLA` modules switch on `IsITSMInstalled` and require `TypeID` (and
`Criticality` for services); in 6.5+ criticality and impact of a *ticket* are dynamic fields
(`ITSMCriticality`, `ITSMImpact`), the general catalog class `ITSM::Core::Criticality` is empty.
