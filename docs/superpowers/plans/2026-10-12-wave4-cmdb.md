# Wave 4: ITSM Phase 2a — Tiqora CMDB (Mode B) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give Tiqora its own CMDB ("Mode B: Tiqora führt das ITSM"): a general catalog, CI classes with a form-based class designer (plus import of Znuny class definitions), configuration items with full version history, diff, attachments and history, fast attribute search on 100k+ CIs, CSV/XLSX import and export with saved mapping templates and bulk edit as background jobs, CI links with admin-managed link types, incident-state propagation and an impact graph, the Mode-B implementation of the CI-provider interface (ticket ↔ CI links), a customer-portal CI view with a CI picker in the portal ticket form, the `ConfigItemUpdate` transition action, and a stable service API that the GenericInterface `ConfigItem*` operations and the Znuny ITSM importer (plan itsm-import) build on.

**Architecture:** A new backend package `tiqora.cmdb` owns every `tiqora_cmdb_*` table and the two generic ITSM link tables `tiqora_itsm_link` / `tiqora_itsm_link_type`. Class definitions are versioned JSON documents (a typed superset of Znuny's `Key/Name/Searchable/Input/CountMin/CountMax/CountDefault/Sub` model). Every CI save goes through `CiService`, which validates values against the class's current definition, writes a new `tiqora_cmdb_ci_version` row only when data changed, maintains the denormalised search index `tiqora_cmdb_ci_attr`, writes a history row and recomputes derived incident states along propagating links (bounded BFS with a job fallback). Search compiles the wave-0 filter JSON onto `tiqora_cmdb_ci` plus `EXISTS` sub-queries on the index, scoped by the class's Znuny group (ro/rw). Imports, exports, bulk edits, full propagation recomputes and the version archive run as wave-0 jobs. The whole surface is gated by `itsm.mode == "tiqora"` through one seam (`tiqora.cmdb.gate`) that is wired to the itsm1 plan's resolver at merge time. The frontend adds an agent "CMDB" area (list/search, CI detail with versions/diff/links/impact graph, create/edit form rendering nested groups), admin screens (catalog, classes + designer, link types), an import/export wizard, two new field kinds (`ci_ref`, `company`) and two portal pages.

**Tech Stack:** FastAPI, SQLAlchemy 2 async (MariaDB and PostgreSQL), pydantic v2, PyYAML, openpyxl (already a dependency), pytest + testcontainers; React 19, TanStack Router + Query, Tailwind tokens, i18next, `@xyflow/react` 12.12.0 (already a dependency, used by the process designer), Vitest, Playwright (demo mode). **No new dependency** on either side.

**Spec:** `docs/superpowers/specs/2026-10-08-itsm-cmdb-design.md` — "Fixed decisions → 1, 1a (Mode B, add-on views)", "Scope → B. CMDB" (tables and features), "GenericInterface" (`ConfigItemUpdate` action), "Tests" (definition validation, version diffing, attribute index consistency, incident propagation incl. cycles, impact traversal limits), "Phases → 2" (the CMDB half), "Risks / open" (CMDB size: paging and archive policy). Master: `docs/superpowers/specs/2026-10-08-competitive-parity-roadmap-design.md` → "Waves", row 4 ("ITSM 0–2 (core, incident/problem, Mode A, CMDB, importer, `TiqoraITSM` add-on)"). Binding product decision (2026-10-12): `itsm.mode` (`off | znuny_readthrough | tiqora`) defaults automatically — Znuny ITSM tables present → `znuny_readthrough` (Mode A), otherwise `tiqora` (Mode B); switching A→B is only ever an explicit admin action (importer run); docs recommend Mode B as the target. Builds on the wave-0 foundations (jobs, typed field engine, filter model, extension registry, settings sections) and the wave-3 transition-action registry (`tiqora.process.actions.registry`).

## Open questions for the product owner

Each item is decided conservatively in this plan and marked "Assumption:" where it applies.

1. **Access model.** CMDB access is per class through the class's Znuny group: `ro` reads, `rw` creates/edits/deletes/links. There is no extra CMDB-wide group (Znuny's `itsm-configitem`); an agent sees the CMDB menu when they have `ro` on at least one class group; admins see everything.
2. **CMDB in Mode A.** While `itsm.mode` is `znuny_readthrough`, every Tiqora-CMDB endpoint answers 409 ("Die CMDB wird in Znuny geführt") except `GET /cmdb/status`; admins cannot prepare classes in Tiqora before the importer switch. With `off` the endpoints answer 404 and the menu is hidden.
3. **CI numbers.** `number = number_prefix + 6-digit per-class counter`; the default prefix is the upper-cased class key plus `-` (e.g. `SERVER-000042`), editable per class. Imported Znuny numbers are kept verbatim.
4. **Values that the current class definition no longer knows** are dropped on the next save (Znuny behaviour), but only after the editor confirmed it (`drop_unknown: true`; otherwise 422 listing the keys).
5. **Delete is a hard delete** (Znuny parity): CI, versions, archive rows, index rows, history, attachments and every `tiqora_itsm_link` row of the CI. Needs `rw` on the class.
6. **Link permission.** Every link needs `rw` on the CI's class; a ticket link additionally needs `rw` on the ticket's queue (Znuny `LinkObject` needs `rw` on both objects). Links to customers, companies, services and KB articles need nothing beyond the class right.
7. **Ticket ↔ CI links in Mode B** write no Znuny `ticket_history` row. They write the outbox event `LinkAdd`/`LinkDelete` with `{"target_object": "ITSMConfigItem", "target_key": "<ci id>"}` (the payload `link_objects` already writes for Mode-A CI links), so SSE, webhooks and the ticket cache behave the same in both modes. Default link type is `RelevantTo` (Znuny's default for ticket ↔ CI).
8. **Portal visibility.** A customer sees a CI only when its class has `portal_visible = true` and the CI is linked to the customer user or to one of the customer's companies (primary `CustomerID` plus `customer_user_customer` mappings), independent of the "company tickets" setting. Only attributes flagged `portal: true` in the definition are shown. Defaults: both off.
9. **Propagation semantics.** A CI whose own incident state has functionality `incident` puts every CI that depends on it (transitively, along link types whose `propagation` points that way) into the catalog's `warning` state; services linked through a propagating link get `warning`, never `incident`. Seeded types: only `DependsOn` propagates (`to_source`, Znuny `ITSM::Core::IncidentLinkTypeDirection` default); the importer may change this per site.
10. **No auto-seeded classes.** A fresh install has no CI classes. The class list offers five built-in templates (Computer, Hardware, Location, Network, Software, modelled on Znuny's defaults with fewer attributes) that an admin applies with one click.
11. **Import defaults:** `on_error = "abort"` (a file with any invalid row writes nothing; the report lists every problem) and `empty_cells = "keep"` (an empty cell keeps the stored value). Both are switchable per run and per mapping template.
12. **Version archive** is off by default. When switched on, a daily service moves versions that are both older than 365 days and beyond the newest 50 of a CI into `tiqora_cmdb_ci_version_archive`; archived versions stay viewable ("Ältere Versionen laden"). Nothing is ever deleted by the archive.
13. **`ConfigItemUpdate` transition action** accepts `ConfigItemID` / `ConfigItemNumber` (comma lists), `Name`, `DeplState`/`DeplStateID`, `InciState`/`InciStateID` and top-level attribute keys; it runs as the acting user without a class permission check (transition actions in Znuny run with `UserID` and check nothing) and does nothing outside Mode B. Key names to be re-checked against the Znuny 7.3 POD that the itsm1 schema survey records in `docs/itsm-import.md`.
14. **Attribute filters** in the CI search are offered only when exactly one class is selected (attribute keys are per class); across classes there is the free-text search.
15. **Reporting source `config_items` is deferred** (see Deviations): the report engine scopes every source by queue, CIs are scoped by class group.
16. **German terms:** "Verwendungsstatus" (deployment state), "Vorfallsstatus" (incident state), "Klasse", "Version", "Verknüpfung", "Auswirkungen", "Abhängigkeiten", "Zuordnungsvorlage", "Probelauf". Seeded catalog values keep Znuny's English names as data (the importer overwrites them) and get German display labels via i18n keys.
17. **Hidden CIs in the impact graph** (classes the viewer cannot read) are drawn as grey "Kein Zugriff" nodes without number or name, so paths stay visible; they are never expanded further.
18. **Bulk edit** changes only deployment state, incident state and adds one link per CI, for at most 5000 selected CIs per job.
19. **Definition limits:** nesting depth ≤ 5, `count_max` ≤ 100, ≤ 500 attributes per class (all levels).
20. **SQL views for the Znuny add-on** (`tiqora_v1_itsm_ci`, `tiqora_v1_itsm_ci_links`) are created by this plan's migration. If the database user lacks `CREATE VIEW`, the migration logs a warning and continues; `GET /admin/cmdb/status` then shows `views_present: false` and `docs/cmdb.md` names the needed `GRANT`.

## Review Focus

1. **Cycles and caps in incident propagation.** `A DependsOn B DependsOn C DependsOn A` with C in incident must end with C `incident`, A and B `warning`, and terminate; clearing C's incident must return all three to `operational`; deleting the link that carried the warning must clear the downstream warning; a graph larger than `propagation_node_cap` must not be half-updated — the synchronous pass defers to the `core.cmdb_propagation` job and the result says `deferred`. Pinned in Task 12 (`test_cycle_terminates_and_marks_warning`, `test_clearing_incident_clears_cycle`, `test_link_delete_clears_downstream_warning`, `test_cap_defers_to_job_without_partial_update`).
2. **Two agents edit the same CI.** A save with a stale `expected_lock_version` gets 409 "inzwischen geändert", writes no version, no index row and no history row; a save with unchanged data writes nothing and answers `changed: false`. Pinned in Task 6 (`test_stale_lock_version_is_409_and_writes_nothing`, `test_unchanged_save_writes_no_version`).
3. **Import with a bad row in the middle of the file.** With `on_error = "abort"` nothing is written and the report lists the row; with `"skip"` only valid rows are written; a second run of the same file creates no versions (idempotent); an interrupted job re-run converges. Pinned in Task 14 (`test_abort_writes_nothing_on_bad_row`, `test_skip_writes_only_valid_rows`, `test_rerun_is_idempotent`, `test_duplicate_identifier_in_file_is_an_error`).
4. **Portal customer forging another company's CI.** `GET /portal/config-items/{id}` for a CI of another company answers 404 (same body as an unknown id); `POST /portal/tickets` with that id answers 422 and creates no ticket; a CI of a non-portal class is invisible even when linked; attributes not flagged `portal` never appear. Pinned in Task 18 (`test_other_company_ci_is_404`, `test_ticket_create_rejects_foreign_ci_and_creates_nothing`, `test_non_portal_class_hidden`, `test_only_portal_attributes_returned`).
5. **Class definition changes with existing CIs.** After a new definition version removes `CPU` and renames nothing, old versions still render with their own definition (labels intact), the edit form flags `CPU` as unknown, a save without `drop_unknown` answers 422 with `["CPU"]`, and the index for the CI no longer contains `CPU` after a confirmed save. Pinned in Task 6 (`test_save_with_unknown_keys_needs_drop_unknown`), Task 7 (`test_old_version_renders_with_its_definition`) and Task 23 (`CiEditPage` unknown-values warning test).

Also pinned (not top five): search never returns CIs of classes without `ro` and the count never leaks them (Task 8, `test_search_scoped_by_class_group`); attribute index equals a fresh rebuild after every save path (Task 6, `test_index_matches_rebuild`); 100k CIs search < 2 s on both dialects (Task 16, opt-in perf test); the impact graph never names a hidden CI (Task 13); every `/cmdb` route answers 404 in mode `off` and 409 in `znuny_readthrough` (Task 5, `test_mode_gate_on_every_route`); `ConfigItemUpdate` on an unknown number logs and does not stop the transition (Task 19).

```python
# owned by itsm1 (module name per itsm1's plan, assumed tiqora.itsm.provider)
ItsmMode = Literal["off", "znuny_readthrough", "tiqora"]

@dataclass(frozen=True, slots=True)
class CiRef:
    key: str                       # provider-scoped id; Mode B: str(tiqora_cmdb_ci.id)
    number: str
    name: str
    class_key: str
    class_name: str
    deployment_state: str          # display name
    deployment_functionality: str | None   # preproductive|productive|postproductive
    incident_state: str            # display name of the CURRENT (derived) state
    incident_functionality: str | None     # operational|warning|incident
    url: str                       # Mode B: "/agent/cmdb/<id>"; Mode A: Znuny deep link

@dataclass(frozen=True, slots=True)
class TicketCiLink:
    ci: CiRef
    link_type: str                 # e.g. "RelevantTo"
    link_key: str                  # Mode B: str(tiqora_itsm_link.id)

@dataclass(frozen=True, slots=True)
class ImpactSummary:
    affected_ci_count: int
    services: list[tuple[int, str]]          # (service_id, name), first 20
    customer_count: int
    open_ticket_count: int
    truncated: bool

class CiProvider(Protocol):
    mode: ItsmMode
    async def search(self, session: AsyncSession, user_id: int, q: str, *, class_keys: Sequence[str] = (), limit: int = 20) -> list[CiRef]: ...
    async def get(self, session: AsyncSession, user_id: int, ci_key: str) -> CiRef | None: ...
    async def cis_for_ticket(self, session: AsyncSession, user_id: int, ticket_id: int) -> list[TicketCiLink]: ...
    async def link_ticket(self, session: AsyncSession, user_id: int, ticket_id: int, ci_key: str, link_type: str = "RelevantTo") -> TicketCiLink: ...
    async def unlink_ticket(self, session: AsyncSession, user_id: int, ticket_id: int, link_key: str) -> None: ...
    async def tickets_for_ci(self, session: AsyncSession, user_id: int, ci_key: str, *, open_only: bool = False) -> list[int]: ...
    async def cis_for_service(self, session: AsyncSession, user_id: int, service_id: int) -> list[CiRef]: ...
    async def impact_summary(self, session: AsyncSession, user_id: int, ci_key: str) -> ImpactSummary: ...
    async def service_incident_states(self, session: AsyncSession, service_ids: Sequence[int]) -> dict[int, str]: ...
```

### D2. Znuny facts used (and their status)

- **Definition format** (ITSMConfigurationManagement): a list of attribute hashes `{Key, Name, Searchable, Input: {Type, Required?, Size?, MaxLength?, Class? (GeneralCatalog), Translation?, ValueMin?, ValueMax?, ValueDefault?, ...}, CountMin, CountMax, CountDefault, Sub: [...]}`. 6.x stores it as a Perl data-structure string in `configitem_definition.configitem_definition`; 7.x stores YAML (assumed: top-level keys `Pages`/`Sections` plus a `Sections → Content` attribute list in 7.x; the parser accepts both a plain attribute list and the 7.x `Sections` document and takes attributes from every section's `Content`). *Status: from the spec and Znuny 6.x knowledge; 7.x layout to be confirmed by the itsm1 schema survey; the parser keeps unknown keys as warnings, never fails on them.*
- **Input types** → Tiqora types: `Text`→`text`, `TextArea`→`textarea`, `Integer`→`integer`, `Date`→`date`, `DateTime`→`datetime`, `GeneralCatalog`→`catalog` (`Input.Class` → `options.catalog_class`), `CIClassReference`→`ci_ref` (`ReferencedCIClassName` → `options.class_keys`), `Customer`→`customer_user`, `CustomerCompany`→`customer_company`, `User`→`agent`, `Service`→`service`, `SLA`→`sla`, `Queue`→`queue`, `Priority`→`priority`, `Type`→`ticket_type`, `State`→`state`, `TextLink`→`url`, `Dummy`→`group`, `CIAttachment`/`Attachment`→`attachment`; anything else → `text` + warning.
- **Count semantics:** every attribute (not only groups) has `CountMin` (≥ 0), `CountMax` (≥ 1), `CountDefault` (entries shown on a new form); `Sub` may hang under any attribute; `Input.Required` means each present entry needs a value.
- **Version per save:** Znuny writes a version on every save that changes data (`VersionAdd` compares and returns the last version id when nothing changed).
- **History events** (`configitem_history_type`): `ConfigItemCreate`, `VersionCreate`, `DeploymentStateUpdate`, `IncidentStateUpdate`, `ConfigItemDelete`, `LinkAdd`, `LinkDelete`, `DefinitionUpdate`, `NameUpdate`, `ValueUpdate`, `AttachmentAddPost`, `AttachmentDeletePost`. Tiqora uses the same names in `tiqora_cmdb_ci_history.event`.
- **General catalog classes:** `ITSM::ConfigItem::DeploymentState` (preference `Functionality`: `preproductive`/`productive`/`postproductive`), `ITSM::Core::IncidentState` (`operational`/`warning`/`incident`), `ITSM::ConfigItem::YesNo`. Default deployment states: Expired, Inactive, Maintenance, Pilot, Planned, Production, Repair, Retired, Review, Test/QA; default incident states: Operational, Warning, Incident.
- **Link types** (ITSMCore/ITSMConfigurationManagement SysConfig `LinkObject::Type`): `Normal`, `ParentChild`, `DependsOn` ("depends on" / "required for"), `AlternativeTo`, `ConnectedTo`, `Includes` ("includes" / "part of"), `RelevantTo` ("relevant to"). `ITSM::Core::IncidentLinkTypeDirection` default `{DependsOn: Source}`: an incident at the **target** affects the **source**.
- **Ticket ↔ CI** links use link type `RelevantTo` and link object `ITSMConfigItem`.

The links view is written as a `UNION ALL` of the two orientations, so the add-on always reads `(ci_id, object_kind, object_key, link_type, ci_side)`:

```sql
CREATE VIEW tiqora_v1_itsm_ci_links AS
SELECT l.id AS link_id, l.source_key AS ci_key, l.target_kind AS object_kind, l.target_key AS object_key,
       t.type_key AS link_type, 'source' AS ci_side, l.created_at
FROM tiqora_itsm_link l JOIN tiqora_itsm_link_type t ON t.id = l.link_type_id
WHERE l.source_kind = 'ci' AND l.target_kind <> 'ci'
UNION ALL
SELECT l.id, l.target_key, l.source_kind, l.source_key, t.type_key, 'target', l.created_at
FROM tiqora_itsm_link l JOIN tiqora_itsm_link_type t ON t.id = l.link_type_id
WHERE l.target_kind = 'ci' AND l.source_kind <> 'ci';
```

`ci_key` is the CI id as a string (no dialect-specific CAST; the add-on compares strings). `VIEW_DDL: dict[str, str]` in `tiqora/cmdb/views.py` holds exactly these two statements; the migration carries the same literals (migrations import no app code), and a test compares them.

### D4. Definitions and values

```python
# backend/src/tiqora/cmdb/definition.py
AttributeType = Literal[
    "text", "textarea", "integer", "decimal", "date", "datetime", "catalog", "ci_ref",
    "customer_user", "customer_company", "agent", "service", "sla", "queue", "priority",
    "ticket_type", "state", "url", "email", "ip", "mac", "money", "attachment", "group",
]
KEY_RE = r"^[A-Za-z][A-Za-z0-9_]{0,63}$"
MAX_DEPTH = 5; MAX_COUNT = 100; MAX_ATTRIBUTES = 500

class AttributeOptions(BaseModel):          # extra="forbid"
    max_length: int | None = None           # text/textarea/url/email (default 255 text, 20000 textarea)
    min: Decimal | None = None; max: Decimal | None = None   # integer/decimal/money
    currency: str | None = None             # money: ISO 4217, 3 upper letters
    catalog_class: str | None = None        # catalog (required)
    class_keys: list[str] = []              # ci_ref: allowed classes ([] = any)
    multiline: bool = False                 # text shown as textarea in view only

class AttributeDef(BaseModel):              # extra="forbid"
    key: str                                # KEY_RE, unique among siblings
    name: str                               # 1..200
    type: AttributeType
    required: bool = False
    searchable: bool = False                # not allowed for group/attachment
    portal: bool = False                    # shown in the customer portal (Assumption 8)
    count_min: int = 0                      # 0..count_max
    count_max: int = 1                      # 1..MAX_COUNT
    count_default: int = 1                  # count_min..count_max
    default: str | int | None = None        # pre-filled value for new entries (scalar types only)
    help: str | None = None                 # ≤ 500
    options: AttributeOptions = AttributeOptions()
    sub: list[AttributeDef] = []            # allowed under any type; required non-empty for "group"

def validate_definition(attrs: list[AttributeDef], *, known_catalog_classes: set[str], known_class_keys: set[str]) -> list[DefinitionIssue]
    # DefinitionIssue(path: str, code: str, message: str) — codes: duplicate_key, bad_key, depth,
    # count_range, too_many, group_without_sub, searchable_not_allowed, catalog_class_missing,
    # unknown_class_key, bad_default, bad_currency
def iter_attribute_paths(attrs) -> Iterator[tuple[str, AttributeDef]]   # ("NIC", def), ("NIC.IPAddress", def)
def definition_changes(old: list[AttributeDef], new: list[AttributeDef]) -> list[DefinitionChange]
    # DefinitionChange(path, kind: "added"|"removed"|"type_changed"|"count_changed"|"renamed_label"|"flags_changed")
```

Value document (`tiqora_cmdb_ci_version.attributes`):

```json
{"Vendor": [{"v": "Example Corp"}],
 "NIC": [{"v": "eth0", "s": {"IPAddress": [{"v": "192.0.2.10"}, {"v": "192.0.2.11"}]}}],
 "Location": [{"v": 742010}],
 "Specs": [{"v": null, "s": {"CPU": [{"v": 8}], "RAM": [{"v": "16.00"}]}}]}
```

- Every key maps to a list of entries; entry `{"v": scalar | null}` plus `"s"` only when the definition has `sub`.
- Scalars: text/textarea/url/email/ip/mac → `str` (ip normalised by `ipaddress.ip_interface` → `str(ip)` for host addresses, `with_prefixlen` for networks; mac → lower-case colon form); integer → `int`; decimal/money → canonical decimal `str` (`format(Decimal, "f")`, no exponent); date → `"YYYY-MM-DD"`; datetime → `"YYYY-MM-DDTHH:MM:SS"` naive UTC; catalog/ci_ref/agent/service/sla/queue/priority/ticket_type/state/attachment → `int`; customer_user → login `str`; customer_company → customer id `str`; group → `null`.
- `normalize_values(attrs, raw) -> tuple[dict, list[ValueIssue]]` (pure): coerces types, drops entries whose value and subtree are empty beyond `count_min`, enforces `count_min/count_max`, `required`, `max_length`, `min/max`, formats; returns issues with paths like `NIC[1].IPAddress[2]` (1-based) and codes `required`, `too_few`, `too_many`, `bad_type`, `too_long`, `out_of_range`, `bad_format`, `unknown_key`. Unknown keys produce `unknown_key` issues and are removed from the result (the API decides via `drop_unknown`).
- `canonical_json(values) -> str` = `json.dumps(values, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`.
- `collect_references(attrs, values) -> dict[AttributeType, set[int | str]]` (pure); `check_references(session, refs, *, ci_class_filter) -> list[ValueIssue]` loads each set with one IN-list query per type (Znuny tables: `service`, `sla`, `queue`, `ticket_priority`, `ticket_type`, `ticket_state`, `users`, `customer_user`, `customer_company`; Tiqora: `tiqora_cmdb_catalog` with matching `catalog_class`, `tiqora_cmdb_ci` with class filter, `tiqora_cmdb_attachment` bound to this CI or staged by this user) — never a join across the two sides.

### D5. Versions, numbering, locking, history

- `CiService.create(...)`: `next_ci_number(session, class_id)` = `SELECT number_prefix, number_counter FROM tiqora_cmdb_class WHERE id = :id FOR UPDATE` (both dialects support `FOR UPDATE`; no `RETURNING` on MariaDB), `n = counter + 1`, loop while `prefix + f"{n:06d}"` exists in `tiqora_cmdb_ci.number` (≤ 1000 steps, then `NumberExhausted`), `UPDATE tiqora_cmdb_class SET number_counter = :n WHERE id = :id`. `bump_counter_for_number(session, class_id, number)` raises the counter to the numeric suffix of an imported number when the prefix matches.
- Save = compare `(name, deployment_state_id, incident_state_id, canonical_json(values))` with the current version; equal → nothing is written, `changed=False`. Otherwise insert a version with the class's **current** definition id, update the CI row with `UPDATE … SET …, lock_version = lock_version + 1 WHERE id = :id AND lock_version = :expected` (`rowcount == 0` → `CiConflict` → 409), rewrite index rows (`DELETE` + bulk `INSERT` for the CI), write history rows (`VersionCreate` always; `NameUpdate`, `DeploymentStateUpdate`, `IncidentStateUpdate`, `ValueUpdate` with `detail` = `"<path>: <old> → <new>"` truncated to 1000, one row per changed top-level key, at most 20 + `"… (N weitere)"`), then `recompute_from(session, [ci_id])` when the own incident state's functionality changed.
- `drop_unknown`: when the incoming values or the current version carry keys absent from the current definition, `update` raises `UnknownAttributes(keys)` (422) unless `drop_unknown=True`.

### D6. Index and search

- `build_index_rows(attrs, values) -> list[IndexRow]` (pure): for every **searchable** attribute path and every entry: `attr_path` = dotted keys without positions (`NIC.IPAddress`), `position` = running 1-based index within the path, `value_text` = display text cut to 500 (refs: the id as text), `value_key` = `value_text.casefold()[:191]`, `value_num` for integer/decimal/money and every id type, `value_date` for date (midnight) and datetime.
- Filter fields (`cmdb_filter_fields(session, class_id: int | None) -> list[FilterFieldSpec]`): `number` (string), `name` (string), `class` (enum of class keys), `deployment_state` (enum of catalog ids as strings), `deployment_functionality` (enum), `incident_state` (current), `incident_functionality` (enum), `created_at`, `changed_at` (datetime); with `class_id`: `attr.<path>` for each searchable path of the class's current definition, mapped onto the wave-0 `FieldType`s (`id | string | int | datetime | bool | enum`): text-like types (text, textarea, url, email, ip, mac, customer_user, customer_company) → `string` (compared on `value_key`); integer → `int` (on `value_num`); decimal/money → `string` restricted to `ops={eq, neq, is_empty, is_not_empty}` with the compiler comparing `value_num = Decimal(value)` (no new wave-0 field type; range filters on money are a known limitation); date/datetime → `datetime` (on `value_date`, dates as midnight UTC); catalog → `enum` with `enum_values` = the catalog ids as strings; ci_ref/agent/service/sla/queue/priority/ticket_type/state → `id` (on `value_num`). Operators come from the wave-0 `OPS_BY_TYPE`; the wave-0 filter model is used unchanged (`Filter{version: 1, where: <node>}`).
- `compile_ci_search(fields, flt, *, q, class_ids, readable_class_ids) -> Select`: `SELECT tiqora_cmdb_ci.* WHERE class_id IN (:readable ∩ :requested)`; attribute conditions become `EXISTS (SELECT 1 FROM tiqora_cmdb_ci_attr a WHERE a.ci_id = tiqora_cmdb_ci.id AND a.attr_path = :p AND <predicate>)` (`is_empty` → `NOT EXISTS` with a non-null value); `q` → up to 5 whitespace tokens, each must match `lower(number) LIKE %t%` OR `lower(name) LIKE %t%` OR `EXISTS(attr value_key LIKE t%)` (prefix, uses `ix_tiqora_cmdb_ci_attr_key`). `like_escape` on every token.
- `search_cis(session, access, body: CiSearchIn) -> CiPage`: sort `number|name|class|changed_at|deployment_state|incident_state` + `id` tiebreak, `offset`/`limit` (≤ 200), count via `SELECT count(*) FROM (<query> LIMIT 10001)` → `total`, `total_capped = total > 10000`.
- `lookup_cis(session, access, q, *, class_keys, limit=20) -> list[CiRefOut]`: typeahead; exact number match first, then `q` search.

### D8. Links, propagation, impact

- `LinkService.add(session, access, *, source: LinkEnd, target: LinkEnd, link_type_key: str) -> LinkOut` with `LinkEnd(kind, key)`; at least one end is `ci`; type must be valid; non-directed types are stored with the CI on the source side when one end is not a CI, and with the smaller id on the source side for CI ↔ CI; existing identical link → returns it (idempotent); self link → 422. Checks per Assumption 6 (ticket: `PermissionEngine.check(user, ticket.queue_id, "rw")`, loaded by id from `ticket`). Writes history `LinkAdd` on each CI end; for a ticket end writes outbox `LinkAdd` (`_emit_event`) + `invalidate_ticket_cache`. Recomputes propagation when the type propagates and both ends are CIs, or one end is a service (service state is read on demand).
- `LinkService.delete(session, access, link_id)`, `LinkService.list_for(session, access, kind, key) -> list[LinkOut]` (other end resolved to a label: CI number+name (hidden → "Kein Zugriff"), ticket number+title (only with `ro` on its queue; otherwise omitted), service/customer/company/KB names via IN-lists).
- Propagation edges: for link `S —type→ T` with `propagation` = `to_source`: incident at T affects S (edge T→S); `to_target`: S→T; `both`: both.
- `recompute_from(session, seed_ci_ids, *, settings) -> PropagationResult(updated: int, deferred: bool)`: (1) `incident_ids` = CIs whose **own** incident state functionality is `incident` (one query on `tiqora_cmdb_ci` + catalog ids); (2) `warning_set` = BFS from `incident_ids` along propagation edges, layer by layer, loading edges with `SELECT source_key, target_key, link_type_id FROM tiqora_itsm_link WHERE source_kind='ci' AND target_kind='ci' AND link_type_id IN :prop AND (source_key IN :frontier OR target_key IN :frontier)` (chunks of 1000), with a visited set (cycles), depth ≤ 50, node cap `propagation_node_cap`; (3) `scope` = seeds ∪ BFS from seeds along propagation edges (same caps) ∪ CIs whose `cur_incident_state_id` currently is the warning state but are not in `warning_set` and are in the seeds' reach; (4) for each CI in scope: `cur = own if own is incident else warning_state if id in warning_set else own`; write changed rows grouped by new state (`UPDATE … WHERE id IN :ids`). If any cap is hit in (2) or (3): write nothing, enqueue `core.cmdb_propagation` (dedupe key `"all"`) and return `deferred=True`. `recompute_all` (the job) does the same over all CIs in batches of 1000 and commits per batch.
- `service_incident_states(session, service_ids)`: links with one end `service` in ids and the other end a CI, whose type propagates **toward the service end**; a service is `warning` when any such CI's current functionality is `incident` or `warning`; otherwise `operational`. Pure `tiqora_*` queries plus catalog ids.
- `impact_graph(session, access, ci_id, *, depth=2 (1..5), direction="both"|"up"|"down") -> ImpactGraphOut(nodes, edges, truncated)`: BFS over **all** CI ↔ CI links (not only propagating), plus service nodes for CI ↔ service links; node cap `impact_graph_node_cap` (default 300); nodes of unreadable classes become `{"hidden": true}` with no number/name and are not expanded (Assumption 17).
- `affected(session, access, ci_id) -> AffectedOut`: reach = BFS from the CI along propagation edges (what would get `warning`), cap `propagation_node_cap`; services = `service` links of reached CIs (incl. the start) whose type propagates toward the service; customers = `customer_user`/`customer_company` links of reached CIs and services' CIs; open tickets = `ticket` links of reached CIs → ticket ids → `SELECT id, tn, title, queue_id, ticket_state_id FROM ticket WHERE id IN :ids` (IN-list), state type in `OPEN_STATE_TYPES` (state ids resolved first), filtered by `ro` on the queue; each list capped at 50 with total counts; `truncated` when the BFS hit the cap.

### D9. Import, export, bulk, archive (jobs)

- **Upload:** `POST /api/v1/cmdb/import-jobs` (multipart: `file`, `request` JSON = `CmdbImportRequestIn {template_id | mapping + options + class_id, dry_run}`), body limit `import_max_mb` (default 50) via `read_upload_within_limit(file, max_bytes)`. The handler enqueues the job (`kind="core.cmdb_import"`, payload `CmdbImportPayload {user_id, class_id, mapping, options, dry_run, filename}`), then adds the upload as a `TiqoraJobFile(job_id=job.id, name="input-<filename>", ...)` in the same transaction (after `flush()`), and commits; the response is `JobAccepted`. The handler reads the input with `list_job_files` (name prefix `input-`).
- **Targets** (`parse_target(text) -> ColumnTarget`): `number`, `name`, `deployment_state`, `incident_state`, `attr:<Key>[n].<Sub>[m]…` (1-based, default `[1]`, e.g. `attr:NIC[2].IPAddress[1]`), `ignore`. `ImportOptions {delimiter: ";" (csv), encoding: "utf-8"|"cp1252", header_row: bool = True, sheet: str | None, identifiers: list[str] = ["number"] (one of "number", "name", or an `attr:` target of a searchable attribute), empty_cells: "keep"|"clear", on_error: "abort"|"skip", create_missing: bool = True}`.
- **Cell parsing:** states by catalog name or key (case-insensitive); refs: `ci_ref` by CI number, `service`/`sla`/`queue`/`priority`/`ticket_type`/`state` by name, `agent` by login, `customer_user` by login, `customer_company` by customer id, `catalog` by name or key; dates `YYYY-MM-DD` or `DD.MM.YYYY` or an XLSX date cell; datetimes `YYYY-MM-DD HH:MM[:SS]` in the importing user's time zone → UTC (the payload carries `time_zone`).
- **Run:** pass 1 reads all rows (`read_rows`), resolves names with one IN-list per type, matches identifiers (exact; multiple matches → row error; duplicate identifier values inside the file → error on the later rows), builds `RowPlan(row_no, ci_id | None, name, states, values_patch)`, and validates each plan by merging the patch into the current values (`empty_cells`) and running `normalize_values` + `check_references`. Dry run → report. Real run: abort when any row has an error and `on_error == "abort"` (`JobFailed`, report file attached); otherwise pass 2 writes in batches of 200 rows per transaction via `CiService` (`change_note = "Import <filename>"`, `recompute=False`), `ctx.progress` per batch, then one `recompute_from` for all touched CIs (may defer to the job). Report file `report.csv` (`row;status;ci_number;message`, statuses `created|updated|unchanged|error|skipped`), result `{"created", "updated", "unchanged", "errors", "skipped", "dry_run"}`.
- **Export:** `CMDB_EXPORT_JOB` (`core.cmdb_export`), payload `{user_id, class_id, filter, q, file_format: "csv"|"xlsx", template_id | None}`; permission evaluated in the job; columns: `number;name;class;deployment_state;incident_state` + one column per attribute path and entry index up to the maximum count present in the result (cap 10 per path), headers in the `attr:` syntax so the file re-imports with the default mapping; CSV with BOM and `;` like the ticket export; XLSX via `openpyxl.Workbook(write_only=True)`; progress every 500 rows.
- **Bulk:** `CMDB_BULK_JOB` (`core.cmdb_bulk`), payload `{user_id, ci_ids (1..5000), deployment_state_id?, incident_state_id?, link: {link_type_key, target_kind, target_key, ci_side: "source"|"target"}?, change_note}`; per CI: skip without `rw` (reported), update via `CiService.update` with the CI's current `lock_version` (no stale-conflict for bulk), add the link via `LinkService.add`; one propagation recompute at the end.
- **Archive:** `archive_old_versions(session, *, keep, min_age_days, batch=500) -> int` moves versions with `created_at < now - min_age_days` that are not among the newest `keep` of their CI and not the CI's current version into `tiqora_cmdb_ci_version_archive` (`INSERT … SELECT` within `tiqora_*`, then `DELETE`), per batch transaction; the daily worker service `cmdb_version_archive` (03:20) enqueues `core.cmdb_archive` when `version_archive_enabled`.
- **Lanes:** all CMDB jobs run in the `"default"` lane; `core.cmdb_propagation` uses `dedupe_key="all"`.

## Deviations from spec

1. **`tiqora_itsm_link` uses string keys** (`source_key`/`target_key` VARCHAR(100)) instead of `source_id`/`target_id`: customer users and companies have string keys in Znuny.
2. **Incident state is two columns** on `tiqora_cmdb_ci`: `incident_state_id` (own, set by people) and `cur_incident_state_id` (derived); the spec lists one derived column. Znuny keeps both too (`InciStateID` + `CurInciStateID`).
3. **Extra tables** not in the spec's list but needed by its features: `tiqora_cmdb_ci_history` (Znuny history parity), `tiqora_cmdb_attachment` (CI attachments), `tiqora_cmdb_ci_version_archive` (archive policy), `tiqora_cmdb_import_template` (saved mapping templates), `tiqora_cmdb_saved_search` (saved CI searches; the reporting `tiqora_saved_search` table is ticket-specific).
4. **Reporting source `config_items` is not in this plan** (Assumption 15): `ReportSource.scope_column` is a queue column and the compiler scopes by the viewer's queues; CI scope is by class group. It needs a scope abstraction in the report engine first → wave 5 (Reporting 4 / ITSM 3).
5. **Ticket-zoom integration is itsm1's** (C3): this plan delivers the provider, the CI-side "Tickets" tab and `/cmdb/links`; "shown in ticket zoom for linked CIs" is rendered by itsm1's panel through `CiProvider.impact_summary`.
6. **Full-text search is SQL-based** (name/number contains + attribute prefix match) rather than a Meilisearch index; an index enricher can come later.
7. **Out of this plan** (owned elsewhere): Znuny ITSM importer, GI `ConfigItem*`, MCP tools `cmdb_*`, Znuny add-on `TiqoraITSM`, `docs/itsm.md` (itsm-import); QR labels (phase 4); NetBox connector (not wave 4); dashboard ITSM widgets (dashboards phase 3).
8. **No golden test** in this plan: the CMDB has no Znuny wire surface of its own; golden peers have no ITSM packages.
