# Tiqora v0.20.0: wave 5 (approvals, change management, ITSM reports)

Release notes in English; German terms in quotes are the labels in the UI. The version comes from the git
tag; no file carries it. Upgrade steps and failure modes are in
[deployment.md, "Upgrading to v0.20.0"](../deployment.md#upgrading-to-v0200-wave-5). Read them first.
No infrastructure change is required: no new container, role or proxy rule, and no new required setting.
There is one roll-out recommendation: start the api first, and the other roles once it is healthy.

## Highlights

- **Approvals ("Freigaben").** One engine for requests on a ticket: stages and parallel steps, rules (one, all,
  at least n, majority), approvers from agents, groups, roles, approval groups, customer users or dynamic
  sources, deadlines with reminders and escalation, substitutes and forwarding. People decide in "Meine
  Freigaben", in the ticket, through a single-use e-mail link, in the customer portal, through REST, or through
  the MCP tool `approval_decide` (off by default). Guide: [approvals.md](../approvals.md).
- **Change management (Mode B).** A change is a ticket of the change type plus Tiqora's change record: type,
  phase, plans, time window, risk, impact, CAB and review. Tasks, templates and standard changes, a change
  calendar and freeze windows, CAB meetings with agenda and minutes, conflict checks, and a read-only legacy
  archive of Znuny's changes. Guide: [itsm.md](../itsm.md) chapter 8.
- **ITSM reports.** 16 built-in ITSM reports (tickets by type, first-level solution rate, ITSM solution time,
  CIs, changes), and Znuny's ITSM statistics can be imported. Guide:
  [reporting.md](../reporting.md#itsm-reports-and-data-bases).

## What you notice right after the update

- **Approvals are always on; there is no switch.** Every agent gets the "Meine Freigaben" entry, and every agent
  with `rw` on a ticket gets the approvals panel and can start a request, which sends mail.
  `daemon.approvals.enabled` only stops the background service.
- **Reports show a notice for a while.** The report data is upgraded in the background (500 tickets per minute at
  most, newest first; about an hour for 25,000 tickets). Until it is done, first-level and ITSM solution figures
  cover only the tickets recomputed so far. Nothing needs doing.
- **Mode B sites see all 16 ITSM reports**, also when change management is not set up. The ones on CMDB and changes
  are empty then.
- **The sidebar entry "Changes"** appears only once change management is set up (Admin, ITSM, "Einrichten"), or with
  a legacy archive.

## Also in this release

- **Text with emoji is sanitised like on tickets.** Characters outside the Basic Multilingual Plane become U+FFFD
  (�) in approval and change text, in every schema, so a `utf8mb3` database no longer answers such text with
  HTTP 500. The original character is not kept. Details: [approvals.md](../approvals.md#10-annahmen-und-grenzen),
  [itsm.md](../itsm.md#abweichungen-von-znuny).
- New ticket: an internal note ticket for work without a call or mail, which can be dated to when the work was
  done. After a failed send, time booking or change link, the page offers a retry of that step and the link to the
  ticket instead of allowing a second create.
- Phone layout: the agent shell no longer makes pages scroll sideways (one exception under "Known issues"), and
  header popups stay inside the viewport. The wordmark is hidden on phones, and the logo below 360 px.
- Reports: ticket cells link to the ticket; multi-dimension tables no longer list a zero row per day.
- Notifications: `<OTRS_CURRENT_*>` names the agent behind the event.
- Forwarding sends the forwarded article along, and bouncing really redirects the original mail to the new
  recipient only. The phone ticket's acknowledgement hint checks the queue's auto reply.
- AI: transient LLM errors are retried, with a fallback from the final-answer model and a handoff on provider failure.
- Integrations: an outbound-ticket endpoint. Dashboards: edit mode keeps the view's breakpoint.

## Compatibility and limits

**Data protection**

- **Rotating `TIQORA_SECRET_KEY`.** Erasures keep working. Archive runs of the legacy change archive stop. They
  resume with the old key in `TIQORA_ITSM_LEGACY_ERASED_KEY` **only if no erasure ran since the rotation**. If the
  key is lost, or an erasure ran meanwhile (hashes under two keys), they stop for good; the archive stays readable
  and redacted. Rolling back an erasure can be refused in this state when it restores archive rows and hashes of
  other erasures remain. See [deployment.md](../deployment.md#itsm-change-management) and [gdpr.md](../gdpr.md).
- **Mode A and `change_*`.** Tiqora never writes Znuny's `change_*` tables, in any mode. In Mode A erase there. After
  a Mode B import, the same applies to source tables still in place.
- **`tiqora gdpr anonymize-customer`** does not run the CMDB erasure and does not touch approval rows, change records,
  CAB members or the calendar mirror. It does redact the legacy change archive, with permanent tombstones. Use the
  admin erasure for those.

**Rights**

- **Scheduled mails and wallboards** count with the rights of the schedule's owner or the link's creator, also for
  CI classes: recipients see the figures for the classes that person may see, not their own.
- **CAB minutes are visible to every agent.** Agenda lines of changes the reader cannot read are hidden; the minutes
  text is not.
- **The reject comment is required only in the UI.** The service checks only its length, so REST, MCP and link
  callers can reject without one.

**Not built**

- Related tickets use one link type (`related_link_type`), and the change page has no section listing all links as
  Znuny's change zoom does. The API does not restrict by ticket type.
- Type and services cannot be edited after creation **in the UI**. The API allows the type while in draft, and the
  extra services.
- Znuny's change conditions and change notification rules: notifications come from ticket events and the approval
  engine.

**Known issues**

- `/agent/tickets/{id}` at 390 px still scrolls sideways (the page's own content, not the shell).
- The shortcuts help cannot be reached from the header below the `sm` breakpoint (640 px); the `?` key still opens it.
- The admin rebuild of report data does not get past a ticket that fails permanently.
- On the new-ticket page, a network error before a ticket exists shows no message of its own.
