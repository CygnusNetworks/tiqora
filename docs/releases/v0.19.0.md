# Tiqora v0.19.0: wave 4 (ITSM, CMDB, SCIM, plugin extension points)

Release notes in English; German terms in quotes are the labels in the UI. The version comes from the git
tag; no file carries it. Upgrade steps and failure modes are in
[deployment.md, "Upgrading to v0.19.0"](../deployment.md#upgrading-to-v0190-wave-4). Read them first:
there are two infrastructure changes (nginx `/scim/`, compose `service_healthy`) and one roll-out rule
(the ai-worker moves together with api, worker and mcp).

## Highlights

- **ITSM core with Mode A and Mode B.** Incident and problem management in the ticket, major incidents with
  update jobs, a service model with priority matrix (criticality x impact), link types, a link graph and notes
  to linked tickets. The "ITSM-Modus" (Admin, ITSM) decides who owns the configuration items:
  **Aus**, **Znuny führt das ITSM** (Mode A, read-through of the Znuny ITSM tables, read-only) or
  **Tiqora führt das ITSM** (Mode B, recommended). The mode is detected once at the first start and then
  stored. Process `LinkAdd` follows the mode, and a plugin veto skips one action and is reported as
  `skipped_actions`. Guide: [itsm.md](../itsm.md).
- **CMDB (Mode B).** CI classes with versioned definitions, attributes, versions and history, links between
  CIs, tickets and services, impact propagation to service and ticket state, import/export templates,
  attachments, saved searches, bulk jobs, version archive, and the customer portal page "Meine Geräte und
  Systeme". MCP tools `cmdb_search`, `cmdb_get`, `cmdb_impact`. Guide: [cmdb.md](../cmdb.md).
- **ITSM importer and Znuny add-on TiqoraITSM 1.0.0.** Admin, ITSM, "Import aus Znuny" moves classes, CIs,
  versions, history and links from Znuny ITSM to the Tiqora CMDB (dry run, resumable, mapping table) and
  switches Mode A to Mode B; the switch can be rolled back through the importer. Znuny's own CI screens
  become read-only after the switch. The optional Znuny package **TiqoraITSM 1.0.0** (German only; Znuny
  6.0 to 7.3) shows "Betroffene CIs (Tiqora)" in the Znuny ticket zoom and a customer page. It only reads
  two Tiqora views and writes nothing. The GenericInterface gets the `ConfigItem::*` operations. Guide:
  [itsm-import.md](../itsm-import.md).
- **Identity phase 3: SCIM 2.0, step-up MFA, session lifetime per IdP.** Identity providers provision users
  and groups at `/scim/v2` with per-provider bearer tokens (rate limits, lockout for bad tokens, audit
  events); Znuny role writes run in the `scim_role_sync` worker. A provider can require proof of a second
  factor from the IdP (step-up MFA) and can shorten the session lifetime of its logins. SSO-managed
  accounts cannot set a password; plugin password providers skip SCIM accounts that require IdP MFA.
  Guide: [guide/identity-providers.md](../guide/identity-providers.md).
- **Plugin extension points (SDK 0.2.0).** Plugins can register synchronous veto hooks (`before`), write
  through the ticket write services (`as_agent`), channel drivers and notification transports, dynamic field
  types, ticket number generators, mail filters, placeholders, transition actions and conditions of the process
  engine, report sources, password auth providers, customer sources and GenericInterface operations, invokers
  and mappings. The `ai-worker` hosts plugins too. Developer guide:
  [plugins.md](../plugins.md) (Part 2, "Extension points of SDK 0.2.0").
- **Plugin installation from packages and repositories.** Admins install, update and remove plugins in
  Admin, Erweiterungen from a signed `.tqplugin` package or from a package repository (index with publisher
  keys), with a check before anything runs (signature and trust level, pure Python, dependencies, SDK
  compatibility, name collisions). Plugins bring their own database tables and Alembic migrations (tables
  prefixed `tqp_<short id>_`), and the processes restart one after another. Baking plugins into the image
  stays supported and is the only path on read-only containers. Browser sessions only: API keys cannot
  install plugins.

## Also in this release

- Ticket create writes Znuny's initial `ServiceUpdate`, `SLAUpdate` and `TypeUpdate` history rows when
  `Ticket::Service` / `Ticket::Type` are on (history parity with Znuny; nothing changes when both are off,
  as on production).
- Dashboards: the chat queue counts chats the AI assistant answers.
- GDPR anonymise mode drops ticket titles from CMDB link history.
- Fix: a full CMDB recompute no longer overwrites CIs saved while it runs.

## Operator checklist (short form)

| Item | Action |
|---|---|
| nginx | `location /scim/` proxied to `tiqora-api` like `/api/` (only for proxies that list locations) |
| Roll-out | api first, then worker, mcp **and ai-worker**, same image |
| Compose | worker, ai-worker, mcp: `depends_on: tiqora-api: condition: service_healthy` (production compose is outside the repository) |
| Database | `max_allowed_packet` larger than `TIQORA_PLUGINS_MAX_PACKAGE_MB` (default 15, max 25) |
| Migrations | `20261010_0077` to `0082`, `tiqora_*` only, seconds, head `20261010_0082` |
| ITSM mode | auto-detected once: Znuny ITSM tables `general_catalog` and `cip_allocate` present -> Mode A, else Mode B (production: Mode B) |

## Compatibility and limits

- Znuny stays unchanged; the migrations add `tiqora_*` tables and columns only.
- Mode A reads Znuny ITSM versions that were surveyed (see [itsm-import.md](../itsm-import.md)); with an
  unknown version Tiqora shows no CI data and the importer offers "Umstellen ohne CI-Daten".
- The plugin SDK moves to 0.2.0; plugins declaring `sdk = ">=0.1,<0.2"` are shown as "Nicht kompatibel" and need `sdk = ">=0.2,<0.3"` (no other change).
- Plugins run in the Tiqora process with full trust. The signature and trust levels prevent accidents; an
  admin can sign their own package. Do not treat them as a security boundary.
