# Internationalization (UI languages)

Tiqora’s agent, admin, and portal UIs use **react-i18next** with a
Znuny-compatible locale registry.

## Counts vs Znuny

| Source | Count | What it is |
|---|---:|---|
| **Znuny 6.5** `i18n/Znuny/Znuny.<code>.po` | **48** | Translation catalogues (English is the implicit source; there is no `Znuny.en.po`) |
| **Tiqora** UI locales | **49** | Plain **`en`** (source) + all **48** Znuny `.po` codes |

Every Znuny language code is present in Tiqora. There is no Tiqora-only language
and no Znuny language missing from the picker.

Codes match Znuny `UserLanguage` / `.po` names (`de`, `pt_BR`, `zh_CN`, …) so
UI choice, notification language, and legacy preferences stay aligned during
parallel operation.

## What ships

| Item | Location |
|---|---|
| Registry (labels, BCP-47, RTL) | `frontend/src/i18n/locales.ts` (`SUPPORTED_LOCALES`) |
| UI string JSON (full key parity with `en.json`) | `frontend/src/i18n/locales/*.json` |
| Loader / picker helpers | `frontend/src/i18n/index.ts` |
| Preference API | `GET/PUT /api/v1/auth/me/language` → `user_preferences.UserLanguage` |

- **RTL:** `ar_SA`, `fa`, `he` set `dir="rtl"` on `<html>`.
- **Lazy load:** `en` and `de` are eager; other locales load on demand.
- **Picker:** account menu + settings; searchable when the list is long.

## Maintaining translations

```bash
cd frontend
pnpm i18n:check                         # every locale must match en.json keys
pnpm i18n:scaffold -- --code xx         # copy en structure for a new code (English placeholders)
```

**Source of truth for new strings:** add keys to `en.json` and translate them
into every other locale **by hand** (no machine-translation scripts in this
repo). Keep `de.json` current for the day-one pair. After scaffolding a new
language code, replace the English placeholders with real translations before
shipping. `pnpm i18n:check` fails CI if any locale file is missing keys.

## Scope notes

- This catalogue is the **Tiqora UI** string set, not a re-use of Znuny `.po`
  message IDs (different product strings).
- Regional English (`en_CA`, `en_GB`) may intentionally match `en` almost 1:1.
- Backend notification / auto-response templates still resolve language via
  Znuny-compatible preference and template language codes.
